# ADR-0008: Desktop Configuration Ownership

Status: Accepted
Date: 2026-08-07

## Context

Day 4 established the ownership rule for workspace configuration
(ADR-0005): Veilbox owns what it generates, and it never destroys what
the user owns. The desktop extends the same problem into a new
directory tree. A compositor's config (`~/.config/niri/config.kdl`), a
shell's config (`~/.config/noctalia/config.toml`) and Veilbox's own
settings file must each have an explicit owner, or "preserve user
files" degenerates into "never deliver a working desktop" and
"regenerate templates" degenerates into "clobber user work".

The niri config is additionally executable content: niri validates it
at startup, and an invalid file is not "user preference", it is a
broken desktop.

## Decision

### Three ownership tiers

| File | Owner | Veilbox behavior |
|---|---|---|
| `~/.config/niri/config.kdl` | **user after first touch** | first-touch render at install; preserved forever after, even by provision |
| `~/.config/noctalia/config.toml` | **user after first touch** | first-touch render at install; preserved forever after |
| `~/.config/veilbox/desktop/<name>/noctalia-veilbox.toml` | **Veilbox** | regenerated by every provision/install |

First touch wins: on the very first activation Veilbox renders its
templates into the user files (they did not exist, so Veilbox is the
whole content). Every later run — install, provision, reinstall after
remove — reports `preserved <path> (user-owned, not overwritten)`.

The Veilbox-owned file is where the engine can always converge
system-side settings (theme, bar placement, wallpaper path). The
user-facing shell config includes it via TOML `[include]`, with user
values winning over the include — so the user can override anything,
and Veilbox never has to touch the user file to change system
defaults.

### Drift is reported, never silently repaired

Provision and install are conservative by default: user-owned files
are left alone even when they drifted from the template. The engine
reports what it did (`created` / `preserved` / `regenerated`) so the
distinction is always visible in the CLI output.

### Template artifacts never stop being a bug

A template bug that ships a broken generated file is a Veilbox bug.
When a shipped template is fixed, the installed user file is a
bug-affected artifact, not user work: the acceptance procedure
re-renders it (reinstall of the experience package + regenerate) and
the release changelog records it. The rule protects user edits, not
Veilbox bugs.

### Wallpaper and paths resolve at render time

Templates use Go text/template with a small, strict context:
`DisplayName`, `Name` (the experience name) and `SystemDir` (the
shipped template directory). Rendering happens at install/provision
time, so the generated file contains real paths (no template
placeholder ever survives into a live config). The wallpaper path in
the Veilbox-owned settings resolves to the RPM-installed wallpaper,
not into the user directory.

## Consequences

- Veilbox can always repair system defaults by regenerating its own
  file, without violating user ownership.
- User files are never overwritten, even after remove/reinstall.
- The three-tier model is auditable in output: `created`, `preserved`,
  `regenerated` are distinct, explicit verbs.
- First-touch semantics mean the template fix path is
  re-render-with-explicit-record rather than automatic repair.
